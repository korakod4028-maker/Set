Module 10 — Work with Users

การจัดการผู้ใช้งานในระบบ Linux: UID/GID, ไฟล์คอนฟิกผู้ใช้, คำสั่งสร้าง–แก้ไข–ลบผู้ใช้ และแนวทางที่ใช้จริงในงาน Cloud/Network Engineer
id && whoami && cat /etc/passwd | tail -1

01ประเภทของผู้ใช้ใน Linux

ระบบสิทธิ์ของ Linux แบ่งผู้ใช้ออกเป็น 3 ระดับ ซึ่งเป็นพื้นฐานของโมเดล Least Privilege ที่ทีม Cloud/Security ใช้ทุกวัน
ระดับคำอธิบายตัวอย่างการใช้งานจริง
Standard Userสิทธิ์จำกัด เข้าถึงเฉพาะไฟล์/โฟลเดอร์ของตัวเองบัญชี dev ที่ deploy โค้ดแต่แก้ config ระบบไม่ได้
Elevated Userผู้ใช้ทั่วไปที่ถูกอนุญาตให้รันคำสั่งผ่าน sudo ได้บางส่วนหรือทั้งหมดวิศวกรที่อยู่ในกลุ่ม sudo/wheel
Rootสิทธิ์สูงสุด (UID 0) ทำได้ทุกอย่างในระบบควรหลีกเลี่ยงการล็อกอิน root โดยตรง — ใช้ sudo แทนเพื่อเก็บ audit log
มุมมอง Engineer: ในสภาพแวดล้อม Cloud ควรปิดการ SSH login ด้วย root โดยตรง (PermitRootLogin no ใน /etc/ssh/sshd_config) แล้วให้ทุกคนใช้บัญชีของตัวเอง + sudo เพื่อให้ระบุตัวตนผู้กระทำได้ในภายหลัง

02โครงสร้าง UID และ GID

UID (User Identifier) และ GID (Group Identifier) คือเลขที่ระบบใช้อ้างอิงสิทธิ์จริง ๆ เบื้องหลัง — ชื่อผู้ใช้เป็นแค่ label ที่มนุษย์อ่านง่าย
UID 0
root — สงวนไว้สำหรับผู้ดูแลระบบสูงสุดเสมอ
UID 1–99
บัญชีระบบที่ตั้งไว้ล่วงหน้าโดย distro เช่น mail, www-data, bin
UID 100–999
บัญชีระบบ/เดมอนที่ถูกสร้างภายหลังโดยแพ็กเกจต่าง ๆ เช่น mysql, docker
UID 1000+
บัญชี ผู้ใช้งานทั่วไป (ค่าเริ่มต้นตั้งแต่ Ubuntu, Debian, RHEL/CentOS รุ่นปัจจุบัน)
แก้ไขจากเอกสารต้นทาง: ช่วง UID ไม่ได้ตายตัวเป็น "มากกว่า 1000" เสมอไป — ค่าจริงถูกกำหนดโดยตัวแปร UID_MIN และ UID_MAX ใน /etc/login.defs ระบบเก่าบางตัว (RHEL 6 เดิม) เคยตั้ง UID_MIN=500 การเช็กค่าที่แท้จริงในเครื่องควรรัน grep UID_MIN /etc/login.defs เสมอ ไม่ควรท่องจำเลข 1000 แบบตายตัวตอนไปเจอระบบจริง

03ไฟล์คอนฟิกผู้ใช้ 4 ไฟล์หลัก

/etc/passwd — ข้อมูลพื้นฐานผู้ใช้ทุกคน

username:x:1001:1001:Mix K:/home/mix:/bin/bash
   │    │  │    │      │        │        └─ shell เริ่มต้น
   │    │  │    │      │        └─ home directory
   │    │  │    │      └─ description / GECOS
   │    │  │    └─ GID (กลุ่มหลัก)
   │    │  └─ UID
   │    └─ password field = x → รหัสจริงเก็บที่ /etc/shadow
   └─ username
ข้อสังเกต: ถ้าช่อง shell เป็น /sbin/nologin หรือ /usr/sbin/nologin แปลว่าห้าม login แบบ interactive shell — นิยมใช้กับบัญชีระบบ (เช่น service account ของ nginx, mysql) เพื่อลดพื้นผิวการโจมตี

/etc/shadow — รหัสผ่านที่เข้ารหัสแล้ว

เก็บ hashed password และข้อมูลอายุรหัสผ่าน (password aging) ที่ไม่อยู่ใน /etc/passwd เพื่อความปลอดภัย เพราะไฟล์นี้อ่านได้เฉพาะ root เท่านั้น

แก้ไขจากเอกสารต้นทาง: ความหมายของสัญลักษณ์ในช่องรหัสผ่านมีรายละเอียดมากกว่าที่สรุปไว้ ควรแยกให้ชัดดังนี้:
สัญลักษณ์ความหมาย
! หรือ !!บัญชีถูก ล็อก (locked) — มักเกิดจาก passwd -l หรือบัญชีที่ยังไม่เคยตั้งรหัสผ่านเลย ทำให้ login ด้วยรหัสผ่านไม่ได้ (แต่ถ้ามี SSH key ตั้งไว้ ก็ยัง login ผ่าน key ได้ปกติ — เป็นแนวทางที่ปลอดภัยสำหรับ service account)
*บัญชี ปิดใช้งานถาวร ด้วยรหัสผ่าน (มักใช้กับ system account ที่ไม่ควร login ได้เลย)
string ยาวขึ้นต้นด้วย $6$...Hash รหัสผ่านจริง (เลข 6 คือ SHA-512)

/etc/group — ข้อมูลกลุ่ม

developers:x:1002:mix,anan,ploy
   │         │  │    └─ รายชื่อสมาชิกกลุ่มรอง (secondary members)
   │         │  └─ GID
   │         └─ password field (แทบไม่ใช้แล้ว)
   └─ group name

/etc/gshadow — รหัสผ่านกลุ่ม (เข้ารหัส)

เก็บ hashed password ของกลุ่ม และรายชื่อ group administrator — ปัจจุบันใช้งานน้อยมากเพราะการยืนยันตัวตนระดับกลุ่มถูกแทนที่ด้วย sudo/RBAC เกือบทั้งหมด

04คำสั่งตรวจสอบตัวตน

คำสั่งใช้ทำอะไร
whoamiบอกว่ากำลังล็อกอินเป็นผู้ใช้คนไหน (ไม่รับ argument ชื่อผู้ใช้อื่น)
idแสดง UID, GID, กลุ่มหลัก, กลุ่มรอง ของผู้ใช้ปัจจุบัน
id <username>ตรวจสอบ UID/GID ของผู้ใช้อื่นได้ เช่น id ubuntu
groupsแสดงรายชื่อกลุ่มทั้งหมดที่ผู้ใช้ปัจจุบันเป็นสมาชิก

05useradd vs adduser

useraddadduser
ชนิดโปรแกรมBinary (compiled) — มีในทุกตระกูล LinuxPerl script ที่เรียก useradd ทำงานเบื้องหลัง
โหมดทำงานไม่ interactive — รันคำสั่งเปล่าๆ จะไม่สร้าง /home และไม่ตั้งรหัสผ่านให้Interactive — ถามรหัสผ่าน สร้าง /home และกำหนด shell ให้อัตโนมัติ
ความพร้อมใช้งานมีในทุก distro เสมอเดิมมีเฉพาะ Debian/Ubuntu เป็นหลัก
แก้ไขจากเอกสารต้นทาง: ข้อสรุปที่ว่า "adduser เป็น Perl script" ถูกต้องสำหรับตระกูล Debian/Ubuntu (ซึ่งเป็นฐานที่ LFCS ใช้สอน) แต่ในตระกูล RHEL/CentOS/Fedora/Amazon Linux คำสั่ง adduser มักเป็นแค่ symbolic link ไปยัง useradd ไม่ใช่ Perl script และไม่ interactive — สำคัญมากถ้าคุณต้องทำงานข้าม distro ในสาย Cloud/Network Engineer ให้เช็กด้วย file $(which adduser) ก่อนสรุปทุกครั้ง

06คำสั่งจัดการผู้ใช้ (Cheat Sheet เชิงลึก)

สร้างผู้ใช้

useradd mix -m -s /bin/bash -c "Mix Korakod"
# -m สร้าง /home/mix
# -s กำหนด shell
# -c ใส่คำอธิบาย (GECOS)

ตั้ง/เปลี่ยนรหัสผ่าน

passwd mix

แก้ไขผู้ใช้

usermod mix -g developers        # เปลี่ยนกลุ่มหลัก
usermod mix -aG sudo,docker      # เพิ่มกลุ่มรอง (-a append เสมอ!)
usermod mix -d /srv/mix -m       # ย้าย home พร้อมไฟล์เดิม
usermod mix -s /usr/sbin/nologin # ปิด interactive shell
usermod mix -G ""                # ล้างกลุ่มรองทั้งหมด
คำเตือนสำคัญ: การลืม -a ตอนใช้ -G คือหนึ่งใน incident ที่พบบ่อยที่สุดของมือใหม่ — usermod mix -G docker (ไม่มี -a) จะ "เขียนทับ" กลุ่มรองเดิมทั้งหมดแล้วเหลือแค่ docker กลุ่มเดียว ทำให้สิทธิ์อื่นหายไปเงียบ ๆ โดยไม่มี error เตือน

ลบผู้ใช้

userdel -rf mix
# -r ลบ /home และ mail spool ไปด้วย
# -f บังคับลบแม้ยังมี process ค้างอยู่ หรือไฟล์ถูกล็อก

07คำสั่งผู้ช่วยใน Terminal

คำสั่งหน้าที่
which <command>หาตำแหน่ง binary ของคำสั่ง เช่น which useradd → /usr/sbin/useradd
file <path>ดูประเภทของไฟล์ (ELF binary, script, symlink ฯลฯ)
command1 $(command2)Command substitution — เอาผลลัพธ์ของ command2 ไปเป็น argument ของ command1
file $(which adduser)
# Debian/Ubuntu → "Perl script text executable"
# RHEL/CentOS   → "symbolic link to useradd"

08หัวข้อเสริม — สิ่งที่เอกสารต้นฉบับยังไม่ครอบคลุม

หัวข้อเหล่านี้ไม่ได้อยู่ในเอกสารต้นทาง แต่เป็นความรู้ที่สอบและใช้งานจริงในสาย Cloud/Network Engineer มักถูกถามควบคู่กันเสมอ

8.1 การล็อก/ปลดล็อกบัญชี

passwd -l mix     # ล็อกบัญชี (เติม ! หน้า hash ใน /etc/shadow)
passwd -u mix     # ปลดล็อก
usermod -L mix    # เทียบเท่า passwd -l
usermod -U mix    # เทียบเท่า passwd -u

8.2 Password Aging ด้วย chage

chage -l mix              # ดูข้อมูลอายุรหัสผ่านของ mix
chage -M 90 -W 7 mix      # รหัสหมดอายุทุก 90 วัน เตือนล่วงหน้า 7 วัน
ทำไมต้องรู้: ข้อกำหนด compliance ระดับองค์กร (เช่น ISO 27001, PCI-DSS) มักบังคับ password rotation policy — chage คือคำสั่งที่ใช้บังคับ policy นี้ในระดับ OS

8.3 /etc/login.defs — ค่าเริ่มต้นระดับระบบ

ไฟล์นี้กำหนดค่าเริ่มต้นตอนสร้างผู้ใช้ เช่น UID_MIN, UID_MAX, PASS_MAX_DAYS, PASS_MIN_LEN — เป็นจุดแรกที่ engineer ควรเปิดดูเวลาต้อง harden เซิร์ฟเวอร์ใหม่

8.4 sudo และ visudo

การให้สิทธิ์ elevated ไม่ควรแก้ /etc/sudoers ตรง ๆ ด้วย text editor ทั่วไป เพราะถ้า syntax ผิดจะทำให้ sudo พังทั้งระบบ ต้องใช้ visudo ซึ่งเช็ก syntax ก่อน save เสมอ

visudo
# เพิ่มบรรทัด: mix ALL=(ALL) NOPASSWD:ALL   (ให้สิทธิ์แบบไม่ถามรหัส — ใช้ระวังในโปรดักชัน)

8.5 su vs sudo -i vs sudo -s

คำสั่งพฤติกรรม
su - mixสลับผู้ใช้แบบเต็มรูปแบบ พร้อม environment ของ mix (ต้องรู้รหัสผ่าน mix)
sudo -iเข้าสู่ root shell แบบมี environment ของ root (ต้องรู้รหัสผ่านตัวเอง ไม่ใช่ของ root)
sudo -sเข้าสู่ root shell แต่ใช้ environment เดิมของผู้ใช้ปัจจุบัน

8.6 มุมมอง Cloud/Automation

เชื่อมโยงกับงานจริง: ในสภาพแวดล้อม Cloud แทบไม่มีใครรัน useradd ด้วยมือแล้ว — งานจัดการผู้ใช้ถูกทำผ่าน Infrastructure as Code แทน:
  • cloud-init — สร้างผู้ใช้และ inject SSH public key อัตโนมัติตอน provision VM ใหม่ (ตรงกับแนวคิด "! ใน shadow ปลอดภัยถ้ามี SSH key")
  • Ansible — module ansible.builtin.user จัดการ create/modify/delete user แบบ idempotent ทั้ง fleet เซิร์ฟเวอร์
  • IAM (AWS/GCP/Azure) — แนวคิด UID/GID + group membership บน Linux เทียบเคียงได้กับ IAM User + IAM Group + Policy บน cloud platform

LABสร้างและจัดการผู้ใช้แบบมืออาชีพ

สถานการณ์: คุณเพิ่งได้รับเซิร์ฟเวอร์ Ubuntu ใหม่ ต้องเตรียมบัญชีให้ทีม DevOps ชื่อ nan ให้ทำงานได้ตาม policy ของบริษัท ทำตามทีละขั้นในเทอร์มินัลจริง (VM/VirtualBox/WSL ก็ได้)
1
สร้างผู้ใช้พร้อม home directory และ shell ที่ถูกต้อง
ต้องการให้ nan มี /home/nan และใช้ bash
sudo useradd nan -m -s /bin/bash -c "Nan DevOps"
ตรวจสอบ: รัน id nan ต้องเห็น UID/GID ≥ 1000 และรัน ls /home ต้องเห็นโฟลเดอร์ nan
2
ตั้งรหัสผ่านชั่วคราว
ทีมความปลอดภัยกำหนดให้ผู้ใช้ใหม่ต้องเปลี่ยนรหัสในการ login ครั้งแรก
sudo passwd nan
sudo chage -d 0 nan   # บังคับเปลี่ยนรหัสผ่านทันทีที่ login ครั้งแรก
ตรวจสอบ: chage -l nan ต้องแสดง "password must be changed" หรือ "password expired"
3
เพิ่มเข้ากลุ่ม sudo และ docker โดยไม่ทำกลุ่มเดิมหาย
nan ต้องรัน sudo ได้ และใช้ docker ได้ด้วย
sudo usermod -aG sudo,docker nan
ตรวจสอบ: groups nan ต้องเห็นทั้ง sudo และ docker อยู่ร่วมกับกลุ่มเดิม (ถ้าลืม -a กลุ่มเดิมจะหาย!)
4
สร้าง service account ที่ห้าม login
สร้างบัญชี appsvc สำหรับรันแอปพลิเคชันเท่านั้น ห้ามใครใช้ login เข้าเครื่อง
sudo useradd appsvc -r -s /usr/sbin/nologin
sudo passwd -l appsvc
ตรวจสอบ: grep appsvc /etc/shadow ต้องขึ้นต้นด้วย ! และลอง su - appsvc ต้องถูกปฏิเสธ
5
ตรวจสอบด้วย command substitution
เช็กว่า useradd ในเครื่องนี้เป็น binary จริงหรือ symlink
file $(which useradd)
file $(which adduser)
ตรวจสอบ: เทียบผลลัพธ์กับตาราง useradd vs adduser ในแท็บเนื้อหา ว่าตรงกับ distro ที่ใช้อยู่หรือไม่
6
ล้างระบบ — ลบผู้ใช้ทดสอบ
ลบ nan และ appsvc พร้อมไฟล์ทั้งหมด
sudo userdel -rf nan
sudo userdel -rf appsvc
ตรวจสอบ: ls /home ต้องไม่เห็นโฟลเดอร์ nan เหลืออยู่ และ id nan ต้องขึ้น "no such user"
