mix@ubuntu-server: ~

01 · ภาพรวม

ps คืออะไร และทำไมต้องรู้จัก

ก่อนจะจำ syntax ให้เข้าใจ "ทำไม" ก่อน — เพราะข้อสอบและงานจริงมักถามเชิงสถานการณ์ ไม่ใช่ท่องคำสั่งเปล่า ๆ

แนวคิดก่อน ลองนึกภาพว่าเซิร์ฟเวอร์คือโรงงานที่มีคนงาน (โพรเซส) ทำงานพร้อมกันหลายร้อยคน โดยที่คุณมองไม่เห็นตัวคนงานเลย สิ่งเดียวที่คุณมีคือ "กระดานเช็คชื่อ" ที่บอกว่าใครกำลังทำงาน ใครหยุดพัก ใครติดขัด — ps คือคำสั่งที่ "อ่านกระดานเช็คชื่อ" นั้นให้คุณดู ณ เวลาปัจจุบัน (เหมือนถ่ายภาพนิ่ง ไม่ใช่วิดีโอ)

นิยามทางการ

ps (Process Status) คือคำสั่งที่แสดงสถานะของโพรเซสที่กำลังทำงานอยู่ในระบบ ณ ขณะนั้น ข้อมูลถูกอ่านมาจากไฟล์ระบบภายใต้ /proc/[PID]/ ซึ่งเคอร์เนลอัปเดตอยู่ตลอดเวลา

รันเปล่า ๆ ไม่มี argument

จะเห็นเฉพาะโพรเซสที่ผูกกับ session เทอร์มินัลปัจจุบัน เท่านั้น เช่น shell (bash) และตัว ps เอง — ไม่เห็นโพรเซสของ user อื่นหรือ background service เลย

02 · คอลัมน์ที่ต้องรู้

อ่านผลลัพธ์ของ ps ให้เป็น

คอลัมน์ที่แสดงจะต่างกันไปตามรูปแบบคำสั่ง — สองรูปแบบที่เจอบ่อยที่สุดคือ ps aux (BSD style) และ ps -ef (UNIX style) เพิ่มเติมจากเนื้อหาต้นฉบับ

คอลัมน์ของ ps aux

คอลัมน์ความหมาย
USERเจ้าของโพรเซส (user ที่รันคำสั่งนี้ขึ้นมา)
PIDProcess ID — เลขประจำตัวเฉพาะของโพรเซสนั้น ไม่ซ้ำกัน
%CPUเปอร์เซ็นต์การใช้งาน CPU ของโพรเซส
%MEMเปอร์เซ็นต์การใช้งาน RAM ของโพรเซส
VSZVirtual Memory Size (KB) — หน่วยความจำเสมือนทั้งหมดที่จองไว้
RSSResident Set Size (KB) — หน่วยความจำจริงที่ถูกใช้อยู่ใน RAM ขณะนี้
TTYเทอร์มินัลที่เกี่ยวข้อง หากเป็น ? แปลว่าไม่มี controlling terminal (มักเป็น daemon/background service)
STATสถานะการทำงานของโพรเซส (ดูรายละเอียดหัวข้อถัดไป)
STARTเวลาที่โพรเซสเริ่มทำงาน
TIMEเวลา CPU สะสมทั้งหมดที่โพรเซสใช้ไป (ไม่ใช่เวลาที่ทำงานผ่านมา)
COMMANDชื่อคำสั่งหรือโปรแกรมที่กำลังทำงาน พร้อม argument

คอลัมน์ของ ps -ef เพิ่มเติม

คอลัมน์ความหมาย
UIDเจ้าของโพรเซส (เทียบเท่า USER ใน ps aux)
PIDProcess ID
PPIDParent Process ID — PID ของโพรเซสแม่ที่สร้างโพรเซสนี้ขึ้นมา (จุดเด่นของ -ef ที่ aux ไม่มีให้เห็นตรง ๆ)
Cเปอร์เซ็นต์การใช้ CPU โดยประมาณ
STIMEเวลาที่โพรเซสเริ่มทำงาน (เทียบเท่า START)
TTY / TIME / CMDความหมายเดียวกับใน ps aux
ทำไมต้องมีสองแบบ ใช้ ps -ef เมื่อต้องการดูความสัมพันธ์ "พ่อ-ลูก" ของโพรเซส (ผ่านคอลัมน์ PPID) และใช้ ps aux เมื่อต้องการโฟกัสที่การใช้ทรัพยากร (CPU/RAM) เป็นหลัก
03 · สถานะโพรเซส

STAT — วงจรชีวิตของโพรเซส

ตัวอักษรแรกของ STAT บอกว่าโพรเซส "กำลังทำอะไร" ที่ต้องเข้าใจลึกที่สุดคือความต่างระหว่าง S, D และ Z เพราะเป็นสิ่งที่ระบบจริงพังบ่อยที่สุด

R = Running/Runnable
S = Interruptible sleep
D = Uninterruptible sleep
T = Stopped
Z = Zombie
I = Idle (kernel thread)

⚠ ทำไม D อันตรายกว่า S

โพรเซสในสถานะ S รอสัญญาณทั่วไปและ ขัดจังหวะได้ — สามารถ kill ได้ทันที แต่โพรเซสในสถานะ D กำลังรอ I/O ระดับ hardware (เช่น อ่านดิสก์ที่เสีย หรือ NFS ที่ต่อไม่ติด) จึง ขัดจังหวะไม่ได้แม้แต่ SIGKILL (-9) ต้องรอให้ I/O เสร็จหรือ hardware ตอบกลับก่อนเท่านั้น — เป็นสาเหตุคลาสสิกที่เซิร์ฟเวอร์ "ค้าง" แบบสั่งอะไรก็ไม่ตอบ

👻 Zombie (Z) จัดการยังไง

Zombie คือโพรเซสที่ทำงานเสร็จแล้ว แต่โพรเซสแม่ยังไม่เรียก wait() เพื่อเก็บ exit status มันไม่กิน CPU/RAM แต่จะไปจองช่องว่างในตาราง PID ไว้เฉย ๆ วิธีแก้คือไม่ต้อง kill ตัว zombie เอง (เพราะมันตายไปแล้ว) แต่ต้องแก้ที่โพรเซสแม่ — restart หรือ kill โพรเซสแม่แทน

รหัสเสริม (ตัวอักษรที่สอง)

<

High-priority — ความสำคัญสูง

N

Low-priority / Nice — ความสำคัญต่ำ

s

Session leader — หัวหน้า session

l

Multi-threaded — ทำงานหลายเธรด

+

Foreground — ทำงานอยู่ฉากหน้า

04 · คำสั่งย่อยยอดนิยม

สำหรับ System / Cloud Admin

ps aux
นิยมที่สุด! แสดงโพรเซสทั้งหมดในระบบ (ทุก user) พร้อมรายละเอียด CPU/RAM
USER PID %CPU %MEM STAT START TIME COMMAND root 1 0.0 0.1 Ss 08:00 0:02 /sbin/init www-data 812 12.4 3.2 R 09:15 4:10 nginx: worker process
ps -ef
นิยมใช้ค้นหา PID แบบรวดเร็ว และดูความสัมพันธ์ผ่านคอลัมน์ PPID
UID PID PPID C STIME TTY TIME CMD root 1 0 0 08:00 ? 00:00:02 /sbin/init root 812 1 9 09:15 ? 00:04:10 nginx: master process
ps aux --forest
แสดงโพรเซสทั้งหมดพร้อมโครงสร้างต้นไม้ เห็นความสัมพันธ์แม่-ลูกชัดเจน
root 812 nginx: master process www-data 813 \_ nginx: worker process www-data 814 \_ nginx: worker process
pstree
ดูโครงสร้างความเชื่อมโยงของโพรเซสแบบภาพรวมย่อ ๆ (กระชับกว่า --forest)
init─┬─nginx─┬─nginx │ └─nginx └─sshd───bash───ps
ps aux --sort=-%mem เพิ่มเติม
เรียงลำดับโพรเซสจากใช้ RAM มากไปน้อย — คำสั่งที่ใช้บ่อยที่สุดตอนไล่จับโพรเซสกินแรมบนคลาวด์ (เปลี่ยนเป็น --sort=-%cpu เพื่อดู CPU แทน)
$ ps aux --sort=-%mem | head -6
รู้ไว้ ps รับทั้ง argument แบบมีขีด - (UNIX style เช่น ps -a) และไม่มีขีด (BSD style เช่น ps a) ซึ่งให้รูปแบบผลลัพธ์ต่างกันเล็กน้อย — ที่มาคือ ps ยุคใหม่ (procps) รวมสองมาตรฐานเก่าเข้าด้วยกัน
05 · การกรองข้อมูล

เป้าหมายคำสั่ง

06 · เชื่อมกับสาย Cloud Engineer

ทำไมเรื่องนี้สำคัญกับงานจริง

บนเซิร์ฟเวอร์คลาวด์ (EC2, Compute Engine ฯลฯ) ไม่มี Task Manager แบบ Windows ให้คลิก — ps คือเครื่องมือวินิจฉัยด่านแรกเสมอ

สถานการณ์ 1 · Memory Alert

CloudWatch แจ้งเตือนว่า EC2 instance ใช้ RAM 92% คุณ SSH เข้าไปเพื่อหาตัวการที่กินแรมมากที่สุด 5 อันดับแรก

ps aux --sort=-%mem | head -6
สถานการณ์ 2 · Zombie Buildup

เห็นโพรเซสสถานะ Z หลายสิบตัวสะสมอยู่ ทำให้ใกล้ชนขีดจำกัดจำนวน PID ของระบบ วิธีแก้ที่ถูกต้องคือทำอย่างไร

หา PPID ด้วย ps -ef แล้ว restart โพรเซสแม่ ไม่ใช่ kill zombie ตรง ๆ
สถานการณ์ 3 · Server ค้างทั้งระบบ

สั่งคำสั่งอะไรก็ไม่ตอบสนอง ตรวจสอบแล้วพบโพรเซสสถานะ D ค้างอยู่นาน คุณจะอธิบายสาเหตุกับทีมอย่างไร

โพรเซสกำลังรอ I/O ระดับ hardware (เช่น disk/NFS มีปัญหา) ซึ่งขัดจังหวะไม่ได้แม้แต่ kill -9

08 · แบบทดสอบ

เช็คความเข้าใจ 8 ข้อ

สิ่งที่เพิ่มเข้ามาจากเนื้อหาต้นฉบับ

  • คอลัมน์เต็มของ ps aux (USER, %CPU, %MEM, VSZ, RSS, START) และ ps -ef (UID, PPID, C, STIME) ที่เอกสารเดิมกล่าวถึงไม่ครบ
  • คำอธิบายเชิงลึกว่าทำไมสถานะ D อันตรายกว่า S และวิธีจัดการ Zombie ที่ถูกต้อง
  • คำสั่งเรียงลำดับ --sort=-%mem / --sort=-%cpu และการเลือกคอลัมน์ด้วย -eo
  • คำสั่งคู่หู pgrep / pkill ที่มักใช้แทน ps + grep + kill
  • สถานการณ์จำลองระดับ Cloud Engineer (EC2 memory alert, zombie cleanup, server ค้าง)
  • แบบฝึกหัดพร้อมเฉลยและแบบทดสอบแบบโต้ตอบ
