Network basic 17 — Network Troubleshooting

ping · ipconfig · nslookup · tracert · netstat — สรุป คำสั่ง วิเคราะห์อาการ และแบบฝึกหัด สำหรับเตรียมเป็น Cloud Engineer

1. แนวคิดหลักของ Troubleshooting

เป้าหมาย: "แยกชั้นปัญหา" ให้เร็วที่สุด

ปัญหาเครือข่ายอาจอยู่ที่ IP config → Local network → Gateway/Routing → DNS → Application/Port ห้ามเดาว่า "เน็ตเสีย" ให้ทดสอบทีละชั้นแล้วตัดสาเหตุออก 
1) ipconfig /all        → IP, Mask, Gateway, DNS ถูกไหม? (169.254.x.x = DHCP ล้มเหลว)
2) ping 127.0.0.1       → TCP/IP stack ของเครื่องเองปกติไหม
3) ping [Gateway]       → ออกจาก LAN ได้ไหม
4) ping 8.8.8.8         → ออกอินเทอร์เน็ตด้วย IP ได้ไหม
5) ping google.com      → DNS แปลงชื่อได้ไหม (ไม่ได้ → nslookup)
6) tracert [ปลายทาง]    → หยุดที่ hop ไหน
7) netstat -an          → Port/Connection ของ App เปิดอยู่ไหม

5 คำสั่ง = 5 คำถาม (ออกข้อสอบบ่อย)

คำสั่งคำถามที่ตอบ
ipconfigเครื่องฉันตั้งค่า IP อย่างไร
pingติดต่อปลายทางได้ไหม
nslookupชื่อนี้แปลงเป็น IP อะไร (ถาม DNS ตรง ๆ)
tracertpacket ผ่าน router ตัวไหนบ้าง
netstatเครื่องกำลังเชื่อมต่อ/เปิดพอร์ตอะไรอยู่
หลักสำคัญ: ping ผ่าน = ถึง IP ได้ (Layer 3) เท่านั้น ไม่ได้พิสูจน์ว่า Application ใช้ได้ ส่วน ping ไม่ผ่าน ≠ เครือข่ายเสียเสมอไป เพราะ Firewall/Security Group อาจบล็อก ICMP

nslookup · tracert · netstat

nslookup www.cisco.com            # ถาม DNS ที่ตั้งไว้
nslookup www.cisco.com 8.8.8.8    # ถาม DNS ตัวที่ระบุ (แยกว่า DNS ตัวเดิมเสียไหม)
tracert -d www.cisco.com          # -d ไม่ resolve ชื่อ เร็วกว่า
netstat -an                       # ทุก connection/port แบบตัวเลข
netstat -ano                      # + PID ของโปรเซส
netstat -r                        # ตาราง routing
อ่านผล tracert: * * * = hop นั้นไม่ตอบ ICMP (อาจแค่ปิด ICMP ไม่ได้แปลว่าเสีย) ถ้าทุก hop หลังจากนั้นเป็น * ทั้งหมดจึงสงสัยว่าเส้นทางขาดตรงนั้น

3. Ping ในเชิงลึก

ICMP คืออะไร

ICMP อยู่ที่ Layer 3 (Network) ไม่ใช้ TCP/UDP จึงไม่มีหมายเลขพอร์ต Ping ใช้ Echo Request (Type 8) และ Echo Reply (Type 0) ใน IPv6 ใช้ ICMPv6 ซึ่งสำคัญกว่ามาก (ND, PMTUD) จึงไม่ควรบล็อกทั้งหมด

อ่านผลลัพธ์

Reply from 10.1.1.1: bytes=32 time=2ms TTL=64
time = RTT (ไป-กลับ) · TTL = อายุแพ็กเก็ต ลดลง 1 ต่อ router ค่าเริ่มต้นโดยประมาณ: Linux/Cisco IOS ~64/255, Windows 128 (ใช้เดา OS/จำนวน hop ได้คร่าว ๆ)
ข้อความความหมายจริง
Request timed outไม่มีคำตอบเลย: ปลายทางปิด/บล็อก ICMP/เส้นทางย้อนกลับขาด
Destination host unreachableมี router (หรือเครื่องเอง) ตอบว่าไปไม่ได้ เช่น ไม่มี route หรือ ARP ไม่ได้ผล อ่านดูว่า "Reply from" IP ไหน ถ้าเป็น IP เครื่องเองแปลว่าไม่มี route/gateway
General failureปัญหาที่เครื่องต้นทาง เช่น NIC/driver/ไม่มี IP
TTL expired in transitแพ็กเก็ตวน (routing loop) หรือกำหนด TTL ต่ำเกิน
could not find hostDNS แปลงชื่อไม่ได้ (ยังไม่ได้ส่ง ping)

Loopback และสถิติ

ping 127.0.0.1 (IPv6: ::1) ทดสอบ TCP/IP stack ของตัวเองโดยไม่ออกสาย (ข้อสอบ Q1 ตัวเลือก A คือสิ่งนี้ ไม่ใช่ ping 10.1.1.1) Packet loss สูง = สายหลวม/Wi-Fi แย่/อุปกรณ์โหลดหนัก · ค่า RTT แกว่งมาก (jitter) = เครือข่ายแออัด

5. เนื้อหาเสริมสำหรับ Cloud Engineer

เพิ่มเติม (ต้นฉบับไม่มี) — ส่วนนี้คือสิ่งที่งานจริงใช้บ่อย

APIPA 169.254.0.0/16

ถ้า Windows ขอ DHCP ไม่ได้ จะตั้ง IP 169.254.x.x เอง คุยได้เฉพาะ LAN เดียวกัน เห็นเลขนี้ = ปัญหาอยู่ที่ DHCP/สายเชื่อมต่อ ลอง ipconfig /renew

Ping ผ่านแต่แอปไม่ได้ → ทดสอบพอร์ตจริง

# Windows PowerShell
Test-NetConnection example.com -Port 443
# Linux/macOS
nc -zv example.com 443
curl -v https://example.com        # ดู DNS, TCP, TLS, HTTP ทีละขั้น
curl -I -m 5 http://10.0.1.20:8080

ทำไมใน Cloud ping ไม่ผ่านบ่อย

AWS/Azure/GCP ปิด ICMP ไว้ตามค่าเริ่มต้น ต้องเปิดกฎ Inbound ICMP ที่ Security Group / NSG / Firewall rule และตรวจ NACL (stateless ต้องเปิดทั้งขาไป-กลับ) เช็คลิสต์เมื่อ VM เข้าไม่ได้: 
1. Security Group / NSG เปิดพอร์ต (22/443) และ source ถูกไหม
2. Route table มีเส้นทางไป Internet Gateway / NAT ไหม
3. NACL อนุญาตทั้งสองทิศทางไหม
4. VM มี Public IP / ใช้ NAT ถูกไหม
5. Firewall ในตัว OS (iptables/ufw/Windows Firewall)
6. Service listen ที่ 0.0.0.0 ไม่ใช่ 127.0.0.1 (ดูด้วย ss -tulpn)

MTU ทดสอบด้วย ping

Ethernet MTU 1500 = payload ping สูงสุด 1472 (หัก IP 20 + ICMP 8) · ping -f -l 1472 host ถ้าแตกต้องลดขนาด แสดงว่ามีลิงก์ MTU เล็กกว่า (VPN/Tunnel) พบบ่อยเมื่อเว็บเปิดช้าหรือค้างเฉพาะหน้าใหญ่

DNS ที่ต้องรู้เพิ่ม

Record: A (IPv4), AAAA (IPv6), CNAME (ชื่อแทน), MX (เมล), TXT · มี cache และ TTL ของ record: แก้ DNS แล้วยังเห็นของเก่าให้ ipconfig /flushdns · ถ้า nslookup name ไม่ได้แต่ nslookup name 8.8.8.8 ได้ → DNS ที่ตั้งไว้มีปัญหา

6. จุดที่แก้ไขจากสรุปต้นฉบับ

ผิด/ไม่ชัด: ตาราง "Ping ชื่อสำเร็จ แต่ Ping IP ไม่สำเร็จ" ที่ว่าให้ตรวจ IP ที่ใช้ทดสอบ ในทางปฏิบัติแทบไม่เกิดขึ้น เพราะการ ping ชื่อต้อง ping IP ที่ได้มา ถ้าเกิดจริงมักเป็นเพราะ DNS ให้ IP คนละตัว หรือ IPv4/IPv6 ต่างกัน (ใช้ -4 / -6 แยกทดสอบ)
ผิด: "Ping ทั้งชื่อและ IP ไม่สำเร็จ → สงสัย Network หรือ ICMP ถูกบล็อก" ถูกต้องแต่ครบน้อยไป ต้องแยกต่อด้วย ping Gateway และตรวจ ipconfig ก่อนสรุป
ไม่ครบ: ต้นฉบับอธิบาย TTL ว่าลดลงเมื่อผ่าน router แต่ไม่ได้บอกว่า TTL ที่เห็นคือค่าที่เหลือ ไม่ใช่ค่าตั้งต้น (เช่น 128 → ผ่าน 3 hop เหลือ 125)
ต้องระวัง: ตัวเลือก ping -a (IP→Hostname) ใช้ได้ตามนั้นเฉพาะ Windows · "tracert" เป็นของ Windows (Linux/macOS ใช้ traceroute) · ค่า timeout -w หน่วยเป็น ms ใน Windows แต่ -W หน่วยวินาทีใน Linux
ข้อสอบ Q1: ตัวเลือก A ("TCP/IP stack... without putting traffic on the wire") เป็นคำอธิบายของ ping 127.0.0.1 ไม่ใช่ 10.1.1.1
ไม่ใช่ข้อมูลอ้างอิง: ลิงก์รูป/บทความ Medium ในไฟล์สรุป 17.1.4–17.1.5 ไม่ใช่เนื้อหา Cisco ให้ข้ามได้
